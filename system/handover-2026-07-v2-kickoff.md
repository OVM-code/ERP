**Read `README.md` and `system/instructions.md` first** — they are the current,

delivery methodology that runs as an AI-operated pipeline:

```
requirement meetings → BPA (interactive BPMN doc) → setup plan → FGD → TGD
  → migration → test/UAT → training → manual → aftercare
```

Every stage has: a template in `clients/_template/<stage>/`, a guide in
`docs/<stage>.md`, and validator rules in `tools/check_client.py`. Everything is
demonstrated end-to-end on a fictional client, `clients/_demo-bakkerij-florax/`.
Four skills exist in `.claude/skills/`: `dynamic-report`, `harvest`, `wave-impact`,
`review-system`.

**The component this new work extends** is the BPA system specifically:

## 2. The v2 request, verbatim intent (three asks)

The user gave this as one message, then said "make this version 2 of the system"
before it was interrupted:

1. **PDF export from the HTML BPA page.** The viewer should let the reader export
   either (a) the full BPA or (b) a chosen subset of domains, as a **PDF that uses
   the Cegeka template** (cover page, headers/footers, styling — i.e. it should
   look like an official Cegeka deliverable, not a browser print of the webpage).
2. **Bring Cegeka template visual elements into the HTML page itself** — i.e. the
   *interactive viewer's* look should also draw from the Cegeka template's design
   language (not just the PDF export). Currently the viewer uses a generic
   navy/white palette invented for this project, not Cegeka's actual brand.
3. **A Business Process Catalog system, decoupled from per-client freshness
   checks.** Today `system/instructions.md` step 3 does a *per-client, on-demand*
   freshness check (throttled to once/day) against Microsoft Learn etc. The user
   wants to replace/supplement this with a **standing catalog**:
   - Mirrors the structure of the Cegeka BPA template (domains → scenarios).
   - Represents "all business processes consultants have, at some point, deemed
     settable-up with standard BC" plus "add-on processes that were frequently
     used" — i.e. it's explicitly a **curated, evidence-based catalog**, not a
     literal mirror of the current template content. It should be used to
     **challenge/critique the current `bpa/template/` content** — find gaps,
     stale entries, things the template claims that aren't (or are no longer)
     achievable in standard BC, things the template is missing.
   - Runs its own freshness check **once a month** (not once/day, not per-client)
     and updates itself accordingly.
   - Becomes the **input** that client BPA pages are generated from — i.e.
     `tools/build_bpa.py` / `docs/bpa.md`'s authoring step should reference this
     catalog (or the catalog + template should merge/reconcile) rather than
     consultants working straight off the static template text.

This is explicitly scoped as **"version 2 of the system"** — the user is treating
it as a distinct, versioned iteration, not an incremental patch. Worth confirming
whether they want an actual `v2` branch/tag/changelog marker, or just informal
phrasing for "the next big round of changes."

## 3. What's missing to start — ask the user first

**A. The actual Cegeka visual template file.** The user's message said "attached"
but the request was interrupted before any file upload completed — I checked
`/root/.claude/uploads/` at handover time and found only the original **text**
template (`f4327e79-cegekabpatemplate3.01.md`, already fully imported into
`bpa/template/source-cegeka-process-model-3.01.md`). There is **no visual
asset** (docx/pptx/pdf with the actual Cegeka letterhead, logo, cover page,
colour palette, fonts) anywhere in this session's uploads. **First step in the new
session: ask the user to (re-)attach the Cegeka template file** — ideally the
actual `.docx` with the corporate design, or at minimum a PDF export of it, or the
brand's colour hex codes / logo file / font names if the full template can't be
shared. Do not invent a "Cegeka-style" palette from guesswork.

**B. PDF generation approach — needs a decision, likely with the user.** This repo
is deliberately dependency-free (stdlib Python, vanilla JS, no build step, no
Node in the runtime path — Node/Playwright are dev-only for browser verification).
Options, roughly in order of fit with existing constraints:
   - **Browser print-to-PDF via `@media print` CSS** on the existing viewer
     (`window.print()` triggered from a button) — zero new dependencies, but
     print CSS can only approximate a "template" (running headers/footers with
     logo, precise cover page) — browsers vary in print fidelity and give limited
     control over headers/footers.
   - **Headless Chromium PDF export** (Playwright/Puppeteer at build time, i.e. a
     `tools/build_bpa_pdf.py` that renders the built HTML to PDF with full
     control over margins/headers/footers) — highest fidelity to a real template,
     but introduces a Node+browser dependency into the *delivery* pipeline, not
     just dev-verification. Check whether the target runtime (consultant's
     laptop, CI, Copilot Studio) can have Chromium available.
   - **Separate document-generation path** (e.g. a Python docx/pdf library) that
     builds the PDF directly from the same structured data (`coverage.md`,
     `content/*.md`, `catalog.json`) rather than from the rendered HTML — most
     "template-accurate" (can literally use a Cegeka `.docx`/`.pptx` as a
     starting point via python-docx or similar), but adds a new dependency and a
     second rendering path to keep in sync with the HTML viewer.
   Recommend surfacing these three options to the user with the tradeoff above
   before writing code — this is an architecture decision, not a detail.

**C. Scope of "full BPA vs specific domains" PDF export.** Confirm: is this
per-domain export meant to let a consultant hand a client just e.g. "your Finance
process," independent of what's in-scope for their project? Or should exports
always respect the client's coverage/scope matrix (i.e. never export a domain/
scenario that's out of scope for that client)? This affects whether the export
selector reads from `coverage.md` or from the full catalog.

**D. Catalog "challenge the template" workflow — needs a decided process, not just
a data structure.** The user wants the catalog to actively critique
`bpa/template/`. That implies an output artifact (a diff/report: "catalog says X,
template says Y, here's the evidence") and a human decision point (who approves
updating the template from catalog findings — the existing `system/reviews/`
human-review pattern is the obvious fit, via the `/review-system` skill already
built). Confirm whether template updates from catalog findings should be
auto-drafted-for-review (consistent with everything else in this repo) or fully
manual.

**E. Monthly cadence mechanics.** The existing freshness check
(`system/update-check-log.md`, step 3 of `system/instructions.md`) is
*session-triggered and throttled* (checks once per day *when asked*, not on a
timer — there's no cron/background process in this repo, it's a stateless
assistant). A true "once a month, autonomously" cadence needs either (a) a
Claude Code Routine/cron trigger (the `mcp__Claude_Code_Remote__create_trigger`
tooling is available in this environment and was NOT yet used anywhere in this
repo) that fires monthly and runs the catalog-refresh workflow, or (b) the same
throttle-log pattern as today but keyed to a month instead of a day, checked
opportunistically whenever any session touches the catalog. (a) is a real
"runs itself" system; (b) is "won't re-check twice in the same month if asked."
Confirm which the user actually wants — (a) requires setting up a Routine, which
is a session-affecting action worth confirming before creating.

## 4. Suggested shape for v2 (not yet agreed — proposal to open with)

Once A–E above are answered, a reasonable v2 structure:

- `bpa/catalog/` (new, parallel to `bpa/template/`) — the standing Business
  Process Catalog: same domain/scenario shape as `bpa/template/catalog.json` but
  with its own provenance per entry (source: which past client/SDR/expertise
  entry justified it being "settable up with standard BC," last-verified date,
  confidence). `bpa/template/` stays as "the Cegeka document structure/wording";
  the catalog becomes "the evidence base," and a reconciliation report
  (`bpa/catalog/vs-template-report.md`, regenerated on refresh) is the "challenge"
  artifact from ask 3.
- `bpa/branding/` (new) — extracted Cegeka design tokens (colours, fonts, logo
  asset, cover-page layout) once the real template file is available, consumed by
  both `bpa/viewer/viewer.css` (restyle) and whichever PDF path gets chosen.
- `tools/build_bpa_pdf.py` (new, pending decision B) — full-BPA or
  domain-subset PDF export.
- A monthly Routine (pending decision E) calling a new
  `tools/refresh_catalog.py` + a skill (maybe `catalog-refresh`, following the
  existing skill pattern) that does the actual research/update/reconciliation
  work and drafts changes for human review via `/review-system`.
- `docs/bpa.md` and `system/instructions.md` step 3 get rewritten so
  per-client BPA authoring pulls from `bpa/catalog/` (fresh, evidenced) instead
  of reasoning from `bpa/template/` + ad hoc web checks.
- Version marker: given the user explicitly said "version 2," probably add a
  `CHANGELOG.md` or a `## v2` section somewhere visible (README?) rather than
  silently accumulating — worth asking if they want formal versioning
  (git tag `v2.0`?) given this repo has no version scheme today.
